# Отчёт по индивидуальному заданию 4

**Вариант 27 — однопутный железнодорожный участок**

Выполнила: Харитонова Лилия Геннадиевна  
Группа: БПИ253

## 1. Постановка задачи

Две станции соединены однопутным участком. С обеих сторон прибывают
пассажирские и грузовые поезда. У каждого поезда есть номер, направление,
тип и время прибытия.

Поезда встречных направлений не могут находиться на пути одновременно.
В простом режиме на участке находится не более одного поезда. В групповом
режиме диспетчер может пропустить несколько поездов одного направления,
если есть свободное место, выдержан интервал между въездами и не превышен
максимальный размер группы. Поезд въезжает только с разрешения диспетчера.
Пассажирским поездам можно дать приоритет с учётом времени ожидания.
После прохода участка поезд прибывает на другую станцию.

## 2. Структура проекта

| Файл | Назначение |
| --- | --- |
| `server.c` | диспетчер, состояние участка, обработка подключений |
| `simulation.c` | создание поездов, выбор направления и поезда, проверка состояния |
| `railway.h` | структуры и перечисления модели |
| `config.c` | параметры и их проверка |
| `net.c`, `net.h` | TCP-сокеты, чтение и запись строк |
| `client.c` | клиент поезда и клиент наблюдателя |
| `tests.c`, `test_network.sh` | проверки модели и сетевых сценариев |
| `run_examples.sh`, `run_tests.sh` | запуск примеров и проверок |
| `Makefile` | сборка |

Программы написаны на C и используют IPv4 и TCP. Сервер выполняет роль
диспетчера. Каждый поезд запускается отдельным процессом со своим номером
и TCP-соединением. Наблюдатель тоже работает отдельным процессом. Сервер
хранит общую модель, поэтому на разных компьютерах достаточно указать его
IP-адрес и порт.

Сервер использует неблокирующие сокеты и `poll`. Пока один клиент ждёт ответ,
сервер обрабатывает остальные соединения и обновляет состояние участка.
Состояние модели изменяется в одном цикле, поэтому для него не нужны
мьютексы. Для каждого соединения хранятся незаконченная входная строка и
буфер исходящих данных. Если буфер переполняется, сервер закрывает это
соединение и продолжает обработку остальных. Для обмена по сокетам и записи
журнала используются файловые дескрипторы.

## 3. Ход моделирования

Сервер формирует поезда с номерами от 1 до общего количества. Первые
`left` номеров едут L-R, остальные R-L. Тип и время прибытия формируются
по заданным параметрам. Время модели отсчитывается с запуска сервера.

1. Поезд подключается и отправляет `TRAIN ID`. Сервер сообщает его
   направление, тип и время прибытия. По наступлении времени прибытия
   подключённый поезд переходит из `PLANNED` в `WAITING`.
2. Диспетчер выбирает направление и поезд. В режиме FIFO сравнивается
   время прибытия, а при равенстве — номер. В режиме приоритета первым
   может пройти пассажирский поезд. Когда самый ранний поезд достигает
   порога ожидания, при выборе в его направлении действует обычная
   очередь. При выборе направления после освобождения пути диспетчер
   также учитывает поезда, достигшие порога ожидания.
3. Диспетчер выдаёт `GO`. Поезд переходит в `PERMITTED` и подтверждает
   въезд сообщением `ENTER`. Сервер проверяет направление, вместимость
   и интервал, записывает время въезда и переводит поезд в `ON_TRACK`.
4. Сервер отмечает прохождение участка. По истечении времени проезда
   поезд переходит в `FINISHED`, освобождает место на пути и прибывает
   на противоположную станцию. Когда путь опустел и выданных разрешений
   больше нет, диспетчер может выбрать новое направление.

У диспетчера одновременно может быть одно неподтверждённое разрешение.
При этом несколько подтвердивших въезд поездов могут находиться на пути.
Группа ограничена заданным размером, поэтому при занятом пути диспетчер
не добавляет к ней поезда бесконечно. Порог ожидания влияет на выбор
очереди. Фактическое ожидание может быть больше, если участок занят,
действует интервал безопасности или поезд потерял соединение.

## 4. Наблюдение и повторное подключение

Клиент наблюдателя отправляет `WATCH` и получает `SNAPSHOT` с направлением,
занятостью, размером группы и числом завершивших поездов. Следом идут строки
`STATE` с состоянием каждого поезда и отметкой о подключении. Дальше
наблюдатель получает общий поток событий. Можно открыть несколько
наблюдателей одновременно, закрыть любой из них и запустить снова.
Повторно подключившийся наблюдатель получает актуальный снимок модели.
Для полного журнала с начала поездки используется файл на сервере.

В журнале и у наблюдателей отображаются `ARRIVE`, `QUEUE`, `DIRECTION`,
`PERMIT`, `ENTER`, `PROGRESS`, `EXIT` и `CLEAR`. В каждой строке есть
модельное время, номер поезда, направление и занятость участка. Клиент
поезда выводит события своего поезда. В конце наблюдатели и сервер выводят
`SUMMARY` с причиной завершения, числом прибывших поездов и групп, средним
и максимальным ожиданием.

Поезд можно закрыть и запустить снова с тем же ID. Новый сеанс заменяет
старое соединение этого номера. Ожидающий поезд сохраняет место в очереди
и может получить разрешение после подключения. Если разрешение осталось
без подтверждения после разрыва соединения, оно отменяется. Для живого
соединения подтверждение ожидается до двух секунд реального времени.
Если поезд уже въехал, сервер продолжает отсчитывать время проезда и
освобождает участок по расписанию. Повторное подключение получает текущее
состояние поезда, поэтому въезда второй раз не происходит.

## 5. Параметры

| Параметр сервера | Значение по умолчанию и назначение |
| --- | --- |
| `IP PORT` | обязательные адрес и порт для прослушивания |
| `--left N`, `--right N` | 7 и 7 поездов, суммарно до 200 |
| `--passenger-percent N` | 50, вероятность пассажирского поезда от 0 до 100 |
| `--arrival-min N`, `--arrival-max N` | 0 и 12, границы времени прибытия |
| `--travel N` | 5, время прохождения участка |
| `--capacity N` | 2, вместимость участка |
| `--gap N` | 2, интервал между въездами |
| `--max-group N` | 3, предел размера группы |
| `--strategy fifo\|priority` | `priority`, стратегия диспетчера |
| `--max-wait N` | 12, порог ожидания для смены приоритета |
| `--seed N` | 42, начальное значение генератора |
| `--delay-ms N` | 0 означает 1 мс на модельную минуту |
| `--until N` | 0, без ограничения модельного времени |
| `--log PATH` | `railway.log`, файл общего журнала |

## 6. Сборка, запуск и завершение

Сборка выполняется командой `make`. Для пробного запуска на одном
компьютере нужно выполнить следующие команды в отдельных терминалах.

```bash
./railway_server 127.0.0.1 41027 --left 1 --right 1 --delay-ms 200
./railway_observer 127.0.0.1 41027
./railway_train 127.0.0.1 41027 1
./railway_train 127.0.0.1 41027 2
```

Для наблюдения с нескольких компьютеров сервер запускается с адресом
`0.0.0.0` или адресом своего сетевого интерфейса. В командах клиентов
указывается доступный IPv4-адрес сервера, например `192.168.1.10`,
и тот же порт. TCP-порт должен быть доступен клиентам.

Сервер завершается после прохождения всех поездов (код 0), при достижении
`--until` (код 2) или после SIGINT/SIGTERM (код 4). При нулевом количестве
поездов сервер сразу выводит итог. Если часть поездов ещё не подключена
или отключилась до въезда, сервер ожидает их для полного прогона.
Ограничение времени и сигналы действуют и в этом случае. При штатной
остановке сервер отправляет подключённым клиентам `STOP`. Клиенты
закрывают сокеты и завершаются с кодом 0. При завершении через Ctrl+C
своего клиента сервер продолжает модель. При неожиданном разрыве TCP
клиент сообщает об обрыве и завершает работу с кодом 1.

## 7. Проверка

Команда `./run_tests.sh --model-only` проверяет переходы состояний,
вместимость, отсутствие встречного движения, интервалы и предел размера
группы. Отдельно проверяются выбор пассажирского поезда, повышение
приоритета после ожидания, отсутствие въезда без разрешения, отмена
разрешения и продолжение проезда после отключения клиента. Разбор
команд проверяется на незавершённой строке и двух строках подряд.

| Сценарий | Прошли | Максимальная занятость | Групп |
| --- | ---: | ---: | ---: |
| Без поездов | 0 из 0 | 0 | 0 |
| Одно направление, вместимость 1 | 8 из 8 | 1 | 8 |
| Два направления, вместимость 1 | 9 из 9 | 1 | 9 |
| Два направления, вместимость 2 | 14 из 14 | 2 | 6 |
| 200 поездов, вместимость 2 | 200 из 200 | 2 | 68 |

Сборка всех трёх программ и тесты модели прошли на macOS arm64.
Полный набор тестов также прошёл в сборке с AddressSanitizer и
UndefinedBehaviorSanitizer. Вывод проверки модели сохранён в
`results/model_tests.log`.

Команда `make test` дополнительно запускает сетевые проверки через
Bash. Они проверяют обычный прогон с FIFO, несколько наблюдателей,
переподключение поезда до и после въезда, разбиение TCP-команды на части,
неверный ID и завершение клиентов по сигналу серверу и по лимиту времени.
`./run_examples.sh 41027` запускает примеры простого и группового режимов
и сохраняет вывод в `results/`.

Сетевые сценарии успешно прошли на macOS arm64 через `127.0.0.1`.
В обоих демонстрационных прогонах прошли все 6 поездов. В простом
режиме получилось 6 групп, в групповом — 2. Журналы наблюдателя
сохранены в `results/simple_observer.log` и `results/group_observer.log`.
Отдельно проверен запуск 200 процессов поездов по TCP. Все 200 поездов
въехали и выехали ровно один раз, максимальная занятость составила 4
при вместимости 8. Сервер с нулём поездов завершился с кодом 0,
некорректные параметры были отклонены с кодом 1.
Финальный архив проверен на Linux aarch64 в Docker. Команда `make test`
собрала все три программы и успешно выполнила тесты модели и сетевые
сценарии на Bash. В том числе проверены переподключение, работа нескольких
наблюдателей и завершение по сигналу и по лимиту времени.
Результаты сохранены в `results/linux_tests.log`.

В отдельном прогоне сервер и клиенты работали в двух контейнерах
одной сети Docker. Сервер слушал на `172.18.0.2:41027`, два поезда
и наблюдатель подключились с `172.18.0.3`. Наблюдатель получил начальный
снимок и итог `reason=completed finished=2/2`. Оба клиента поезда
завершились после сообщения сервера. Сервер завершился с кодом 0.
Проверка проводилась на двух сетевых узлах одного физического компьютера.
