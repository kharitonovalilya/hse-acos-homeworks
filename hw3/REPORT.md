# Отчёт по индивидуальному заданию 3

**Вариант 27 — однопутный железнодорожный участок**

Выполнила: Харитонова Лилия Геннадиевна  
Группа: БПИ253

## 1. Постановка задачи

Две станции соединены одним железнодорожным путём. С обеих сторон к участку
прибывают пассажирские и грузовые поезда. У каждого поезда есть номер,
направление движения, тип и время прибытия.

На участке нельзя одновременно пропускать поезда встречных направлений. В
простом режиме на пути может находиться только один поезд. В групповом режиме
можно пропустить несколько поездов одного направления, если не превышена
вместимость и соблюдается безопасный интервал между въездами.

Диспетчер выбирает направление и выдаёт разрешение на въезд. Пассажирские
поезда могут иметь приоритет, но остальные поезда не должны ждать бесконечно.
Диспетчер и каждый поезд работают в отдельных процессах. Программа должна
завершаться после прохождения всех поездов и при прерывании пользователем.

## 2. Входные параметры

Параметры передаются через командную строку.

| Параметр | Назначение |
| --- | --- |
| `--left N`, `--right N` | количество поездов каждого направления |
| `--passenger-percent N` | вероятность пассажирского поезда от 0 до 100 |
| `--arrival-min N`, `--arrival-max N` | диапазон модельного времени прибытия |
| `--travel N` | время прохождения участка |
| `--capacity N` | вместимость участка |
| `--gap N` | минимальный интервал между въездами |
| `--max-group N` | максимальный размер группы одного направления |
| `--strategy fifo` | выбор по времени прибытия |
| `--strategy priority` | приоритет пассажирских поездов |
| `--max-wait N` | порог ожидания для повышения приоритета |
| `--seed N` | начальное значение генератора случайных чисел |
| `--delay-ms N` | длительность модельной минуты в миллисекундах |
| `--until N` | остановка на указанной модельной минуте |
| `--log PATH` | имя файла подробного лога |

Если параметры не указаны, используются значения по умолчанию. Функция
`read_config` читает аргументы и проверяет, что числа находятся в допустимых
границах. Всего можно создать не более 200 поездов.

Значение `--delay-ms 0` означает быстрый режим: одна модельная минута длится
1 мс. Для более наглядного вывода можно указать `--delay-ms 100`.
Параметр `--until 0` означает, что ограничение времени отключено.

Для независимых программ добавлены режимы `--server SESSION` и
`--train SESSION ID`. SESSION задаёт общее имя сессии, ID — номер поезда,
начиная с 1. Имя содержит от 1 до 40 латинских букв, цифр или символов `_`.
Первые `left` номеров соответствуют направлению L-R, остальные — R-L.
Все параметры модели передаются серверу. Поезд получает свои данные из модели.

## 3. Структура проекта

Программа написана на языке C для Linux с использованием POSIX-семафоров,
разделяемой памяти и очередей сообщений. Проект разделён на несколько файлов.

| Файл | Назначение |
| --- | --- |
| `main.c` | запуск программы, режим сервера или поезда и обработка сигналов |
| `config.c` | значения по умолчанию и чтение параметров |
| `simulation.c` | создание поездов, выбор направления и моделирование |
| `railway.h` | структуры, перечисления и объявления функций |
| `model.h` | общие данные модели и функции доступа к ним |
| `sync.c`, `sync.h` | уведомления через POSIX-семафоры |
| `ipc.c` | создание процессов, память, очередь, подключение и очистка |
| `tests.c` | тесты основных функций и режимов |
| `run_tests.sh` | запуск тестов |
| `run_examples.sh` | запуск подготовленных примеров |
| `run_independent.sh` | отдельные запуски сервера и поездов |
| `Makefile` | команды сборки |

Подготовлены четыре программы с одинаковыми правилами движения.

| Программа | Запуск процессов | Обмен данными | Семафоры |
| --- | --- | --- | --- |
| `railway` | один родитель создаёт всех потомков | разделяемая память POSIX | неименованные в общей памяти |
| `railway_named` | один родитель создаёт всех потомков | разделяемая память POSIX | именованные |
| `railway_independent` | сервер и поезда запускаются отдельно | разделяемая память POSIX | именованные |
| `railway_queue` | сервер и поезда запускаются отдельно | очередь сообщений POSIX | именованные |

## 4. Основные структуры данных

Структура `Train` хранит номер поезда, направление, тип, время прибытия,
время въезда, время выезда и текущее состояние.

Состояния поезда заданы `TrainState`:

- PLANNED — поезд ещё не прибыл;
- WAITING — поезд прибыл и ждёт разрешения;
- PERMITTED — диспетчер выдал разрешение;
- ON_TRACK — поезд находится на участке;
- FINISHED — поезд закончил движение.

Структура `Config` хранит все настройки запуска. `Direction` задаёт
свободный участок и два направления движения. `RunResult` задаёт причину
завершения программы.

Структура `Railway` хранит массив поездов, направление, занятость,
статистику, флаг остановки, время начала и семафоры. Дополнительно в ней
хранятся PID подключённых поездов, признак готовности и путь лога.
Указатель `config.log_path` в общей модели равен NULL. Сам путь хранится
массивом символов, потому что адреса независимых процессов могут различаться.

### 4.1. Отображение сущностей в процессы

| Сущность | Представление в программе | Поведение |
| --- | --- | --- |
| поезд | отдельный процесс `train_process` и элемент `Train` | прибывает, ждёт разрешения, проходит участок и выезжает |
| диспетчер | процесс `dispatcher_process` | выбирает направление и выдаёт разрешения |
| станции | направления LEFT и RIGHT и ожидающие поезда | хранят ожидающие поезда каждой стороны |
| однопутный участок | направление и занятость в `Railway` | общий ресурс, доступ к которому защищён семафором |
| родитель в первых двух версиях | функция `run_server` | создаёт потомков, проверяет их завершение и выводит итог |
| сервер независимой версии | отдельно запущенная программа | создаёт IPC, выполняет работу диспетчера и удаляет ресурсы |

Пример сценария взаимодействия:

1. Сервер создаёт модель. Независимые поезда подключаются к его сессии.
2. Два поезда прибывают с разных сторон и переходят в WAITING.
3. Каждый сообщает диспетчеру о прибытии.
4. Диспетчер выбирает направление и отправляет выбранному поезду разрешение.
5. Этот поезд переходит в ON_TRACK. Встречный поезд продолжает ждать.
6. Через заданное время поезд освобождает участок и сообщает диспетчеру.
7. Диспетчер может разрешить движение поезду с другой стороны.

## 5. Работа процессов

Функция `simulate` задаёт имя сессии и вызывает `run_server`. Родитель
создаёт общие данные и запускает потомков через `fork`. Случайные типы и
времена прибытия выбираются до их запуска с помощью `rand`. Параметр seed
позволяет повторить исходные данные на одной системе.

Процесс поезда регистрируется, дожидается времени прибытия, встаёт в очередь
и уведомляет диспетчера. Затем он ждёт разрешения. После разрешения поезд
въезжает на участок, сообщает о прохождении и в конце освобождает место.

Диспетчер проверяет общие данные и условия въезда. Если поезд может въехать,
диспетчер переводит его в PERMITTED и будит именно его процесс.
Переменная `pending` означает, что разрешение уже выдано, но поезд ещё не
въехал. До фактического въезда другое разрешение не выдаётся.

В независимых версиях сервер сам выполняет работу диспетчера. Каждый поезд
запускается отдельной командой и находит данные по имени сессии. Сервер
не создаёт эти процессы и не вызывает для них `waitpid`. Один номер можно
подключить только один раз. Сервер ожидает запуска всех заданных поездов.
Ограничения на время подключения нет.

Время вычисляется по `CLOCK_MONOTONIC`. Общего пошагового цикла для поездов
нет: они выполняются независимо. Во время ожидания разрешения или движения
поезд освобождает доступ к модели, поэтому остальные процессы могут работать.

## 6. Работа диспетчера и синхронизация

Функция `oldest` ищет поезд, который дольше всех ждёт в выбранном направлении.
Если несколько поездов прибыли одновременно, выбирается поезд с меньшим
номером.

При стратегии FIFO диспетчер выбирает самый старый поезд. При стратегии
priority сначала рассматриваются пассажирские поезда. Если ожидание самого
старого поезда достигло `max-wait`, он получает приоритет независимо от типа.

Направление нельзя менять, пока участок занят. Ограничение `max-group`
не позволяет бесконечно продолжать одну группу. Число поездов конечно,
поэтому после обслуживания более ранних поездов остальные также получают
разрешение. Порог ожидания повышает приоритет, но не отменяет правила
безопасности и не задаёт верхнюю границу ожидания.

Общие данные защищены бинарным семафором. Под ним изменяются состояния
поездов, занятость, направление и статистика. Запись событий также выполняется
под семафором, поэтому строки разных процессов не перемешиваются.

У каждого поезда есть семафор `permits[i]` с начальным значением 0.
Диспетчер отправляет разрешение через `sem_post`, а поезд ожидает через
`sem_timedwait`. Семафор `changed` уведомляет диспетчера о прибытии, въезде
и выезде поездов. Ожидание имеет тайм-аут 10 мс для проверки остановки.

### 6.1. Разделяемая память и неименованные семафоры

В `railway` память создаётся через `shm_open`, её размер задаётся через
`ftruncate`, а отображение выполняется через `mmap` с MAP_SHARED.
После отображения файловый дескриптор закрывается. Все потомки используют
одно отображение, унаследованное после `fork`.

Семафоры находятся внутри общей структуры. Для `sem_init` задаётся
`pshared = 1`, поэтому они доступны разным процессам. Объекты `sem_t`
не копируются в локальные переменные. Доступ к модели открывается только
после полной подготовки данных и уведомлений.

### 6.2. Именованные семафоры

В `railway_named` и `railway_independent` данные также находятся в
разделяемой памяти POSIX. Для синхронизации используются именованные
семафоры с правами 0600. При подключении проверяются размер модели
и признак её готовности.

Имя памяти имеет вид `/acos27_SESSION`. Бинарный семафор получает имя
`/acos27_SESSION_s0`, уведомление диспетчера — `_s1`, разрешения поездов
начинаются с `_s2`. Для операций семафор открывается через `sem_open`,
после операции закрывается через `sem_close`. В модели хранится имя,
а не указатель на объект другого процесса.

Для создания используется `O_EXCL`. Если сессия с таким именем уже работает,
повторный сервер получает ошибку. Журнал открывается только после создания
сессии, поэтому повторный запуск не стирает лог работающей программы.

### 6.3. Очередь сообщений

В `railway_queue` разделяемая память не используется. Каждый процесс имеет
локальную копию модели, а актуальное состояние хранится в очереди сообщений
POSIX `/acos27_SESSION`. Семафоры остаются именованными.

Процесс захватывает бинарный семафор, считывает из очереди модель, проверяет
или изменяет её, затем возвращает модель в очередь и освобождает семафор.
Следующий процесс получает уже обновлённые данные.

Модель передаётся частями не больше 8192 байт. В очереди допускается
10 сообщений, поэтому перед запуском проверяется, что размер структуры
не превышает 81920 байт. Все сообщения имеют один приоритет. Общий семафор
не позволяет перемешивать части разных состояний.

Передача выполняется через `mq_timedsend` и `mq_timedreceive` с тайм-аутом
2 секунды. Уведомления `changed` и `permits[i]` работают так же, как в версии
с памятью. Такой способ позволяет сохранить прежние функции модели,
но требует передачи всей структуры при каждом обращении к ней.

## 7. Проверка правил

Перед въездом поезд проверяет разрешение, направление, свободное место
и интервал после предыдущего въезда. Время фактического въезда сохраняется
в `last_entry`.

После въезда и выезда вызывается `valid_state`. Она проверяет:

- число поездов на участке;
- соответствие вместимости;
- одинаковое направление поездов на участке;
- въезд не раньше прибытия;
- длительность завершённого прохождения;
- соответствие сохранённого количества состоянию массива.

Поезд последовательно проходит состояния от PLANNED до FINISHED.
Повторного въезда и выезда в его функции нет. Дополнительно тесты проверяют
по логу, что каждый поезд получил разрешение, въехал и выехал ровно один раз. Также проверяются интервал и размер группы.

Если правило нарушено, создаётся событие INVARIANT и программа останавливается
с кодом ошибки.

## 8. Пользовательский интерфейс и логирование

Пользователь управляет программой через параметры командной строки.
Команда `./railway --help` выводит справку. У независимых программ справка
вызывается через `--server SESSION --help`. При неверном параметре
программа сообщает об ошибке.

В терминал и файл лога выводятся запуск, подключение, прибытие, постановка
в очередь, выбор направления, разрешение диспетчера, въезд, прохождение,
выезд, освобождение участка, предупреждения и итоговая статистика.

Пример строки:

```text
time=00002 event=ENTER     train=005 dir=L-R  occupancy=3 | Поезд въехал на участок
```

- `time` — текущая модельная минута;
- `event` — тип события;
- `train` — номер поезда;
- `dir` — направление;
- `occupancy` — число поездов на участке.

Событие CONFIG содержит PID владельца и имя сессии. REGISTER означает
подключение процесса поезда.
Остальные события сохранены из второй работы.

Для открытия файла используется `open`, для записи — `dprintf` с файловыми
дескрипторами, для закрытия — `close`. Файл открывается с O_APPEND.
Независимые поезда открывают тот же файл для добавления. Относительный путь
преобразуется в абсолютный, чтобы запуск из разных папок не менял место записи.

## 9. Завершение программы

При обычной работе программа заканчивается после прохождения всех поездов.
Параметр `--until` позволяет остановить моделирование на определённой минуте.

Для обработки Ctrl+C и SIGTERM используются сигналы. Обработчик только
устанавливает флаг `stop_requested`. При следующем обращении к модели
процесс устанавливает общую остановку и будит ожидающие процессы.

В первых двух версиях родитель проверяет потомков через
`waitpid(..., WNOHANG)`. Неожиданное завершение потомка останавливает модель.
Перед очисткой родитель собирает всех созданных детей. При ошибке `fork`
уже созданные процессы также получают остановку.

В независимых версиях поезд записывает свой PID только после успешного
открытия лога. Если открыть лог не удалось, регистрация не выполняется,
устанавливается общая остановка с RUN_ERROR и уведомляется диспетчер.
Поезд и сервер завершаются с кодом 1, IPC-объекты удаляются.

Перед отключением поезд сохраняет результат и сбрасывает свой PID.
После остановки сервер даёт подключённым процессам до 2 секунд для выхода.

При остановке выводится частичная статистика. Поезда, не закончившие путь,
не учитываются как завершённые. Среднее ожидание считается среди въехавших.

Очистку выполняет владелец сессии. Неименованные семафоры удаляются через
`sem_destroy`, имена семафоров — через `sem_unlink`, память — через
`shm_unlink`, очередь — через `mq_unlink`. Отображение закрывается через
`munmap`. Учитываются и частично созданные ресурсы. Очистка зарегистрирована
через `atexit`.

## 10. Сборка и запуск

Нужны Linux, компилятор C, make и поддержка POSIX IPC.
Команды выполняются из папки `hw3`.

Сборка и запуск с параметрами по умолчанию:

```bash
make
./railway
```

Пример простого режима:

```bash
./railway --left 3 --right 3 --arrival-max 0 --travel 3 --capacity 1 --gap 1 --max-group 1 --strategy fifo --delay-ms 20
```

Пример группового режима с именованными семафорами:

```bash
./railway_named --left 5 --right 4 --arrival-max 0 --travel 8 --capacity 3 --gap 1 --max-group 3 --strategy priority --delay-ms 20
```

Независимые процессы запускаются из разных терминалов. Сначала сервер:

```bash
./railway_independent --server demo27 --left 1 --right 1 --arrival-max 0 --travel 10 --delay-ms 100 --log demo27.log
```

После строки CONFIG отдельно запускаются два поезда:

```bash
./railway_independent --train demo27 1
./railway_independent --train demo27 2
```

Поезда можно подключать после запуска сервера без ограничения времени.
Для версии с очередью используются те же команды с именем `railway_queue`.
Можно также запустить подготовленный скрипт:

```bash
sh ./run_independent.sh railway_independent demo27 5 4
sh ./run_independent.sh railway_queue queue27 5 4
```

| --- | --- |
| корректные параметры | все поезда проходят участок, код 0 |
| `--until N` | остановка и частичная статистика, код 2 |
| Ctrl+C или SIGTERM | корректная остановка и частичная статистика, код 4 |
| неверный параметр, ошибка выполнения или подключения | код 1 |
| нарушение правила движения | остановка, код 3 |

Для прерывания достаточно Ctrl+C в терминале родителя или сервера.
Можно также отправить `kill -TERM PID`. Для параллельных запусков нужны
разные имена сессий и отдельные файлы лога.

Подготовленные примеры запускаются командой `make examples`.
Команда `make clean` удаляет исполняемые файлы.

Тесты написаны на C и запускаются командой:

## 12. Ограничения

Модель хранит не более 200 поездов. Длина и скорость отдельно не моделируются.
Безопасный интервал задаётся между моментами въезда. Параметр
`passenger-percent` задаёт вероятность типа каждого поезда, поэтому
фактическая доля может отличаться от указанной.

Порядок событий зависит от планирования процессов. Параметр seed повторяет
исходные данные в одной реализации libc, но не фиксирует порядок выполнения.
Результаты повторных запусков и разных версий могут немного отличаться.
После пробуждения время может оказаться больше заданного. Время прохождения
и безопасный интервал при этом не сокращаются.

Версия с очередью передаёт всю модель при каждом доступе. Это увеличивает
объём обмена. Нужны поддержка POSIX mqueue и системные лимиты, допускающие
10 сообщений по 8192 байт. Все процессы работают на одном компьютере
и имеют доступ к одному файлу лога.

SIGKILL и аварийное выключение не позволяют выполнить обработчик сигнала
и очистку. После SIGKILL владельца могут остаться именованные объекты.
Восстановление после гибели процесса внутри критической секции не реализовано:
семафор не освобождается автоматически. Ожидание доступа ограничено примерно
3 секундами, после чего процесс завершает работу с ошибкой. При потере части
модели в очереди её восстановление также не выполняется.

## 13. Итог

В программе реализовано моделирование однопутного участка с использованием
взаимодействующих процессов. Каждый поезд и диспетчер работают отдельно.
Сохранены простой и групповой режимы, две стратегии диспетчера, повышение
приоритета долго ожидающих поездов, логирование и проверка правил.
Подготовлены версии с неименованными и именованными семафорами, независимым
запуском и очередью сообщений. Их работа проверена тестами и примерами.
